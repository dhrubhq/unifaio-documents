# Payment Gateway Framework

Status: v1 (2026-11-02). The contract every online payment gateway (aamarPay, shurjoPay, SSLCommerz, bKash, PortWallet and later ones) implements, and the shared pipelines that sit above it. Product behavior and requirement IDs live in `../02-customer-features/09-payment-integration.md`; provider specifics live in `../03-customer-integrations/gateways/`.

Conflict rule (same as the courier set): `conventions.md` > `domain-model.md` > this framework > `09` > provider doc.

## 1. Goal and non-goals

**Goal.** Any workspace connects its **own** merchant account at any supported gateway, starts a payment for an order (or a custom amount), sends the customer to the gateway, and Unifaio updates the payment and the order from a **verified** result.

**Non-goals.** The platform never holds seller money (funds settle from the gateway to the seller's own account). No card data is stored or seen. Payouts, wallets and subscriptions are out of scope here (`09` P3). Charging the platform's own SaaS plans uses the same framework but the platform's own gateway account (`09` FR-PAY-60).

## 2. Rules (extend `tech-stack.md` section 4)

1. **The adapter is the only code that knows a gateway.** Services, controllers, jobs and the UI talk to the `PaymentGatewayAdapter` contract and the unified statuses. No `if (provider === "aamarpay")` outside `infra/gateways/<id>/`.
2. **A browser redirect is never proof of payment.** Return URLs, `success_url` posts and query strings are *hints*. A payment becomes `paid` only after the adapter's server-to-server `verify` call, made with the workspace's own credentials, says so and the amount matches (`09` FR-PAY-30, FR-PAY-32).
3. **Our reference, never theirs.** Each attempt has its own gateway reference generated by us (section 6.1). References are never reused, even for a retry of the same order.
4. **Money is integer poisha** inside Unifaio. The adapter converts to the gateway's format (decimal string, whole taka, ...) at the edge and converts back; any amount that cannot be represented exactly is refused locally, never rounded.
5. **Tenant isolation.** Gateway accounts, links, attempts and events are tenant tables with `workspace_id` and RLS. The public return and IPN endpoints resolve the workspace from the attempt, never from a request parameter.
6. **Secrets** are encrypted with `CredentialCipher`, masked after save, and never logged or put in an error (redaction test, as for couriers).
7. **Sandbox and live are different accounts.** A gateway account has a `mode`. Sandbox payments never change live finance totals or flip a real order to paid (section 9).
8. **Idempotency everywhere a retry can happen:** creating a link, starting an attempt, handling a return, handling an IPN, verifying.

## 4. The adapter contract

```ts
export type GatewayId = "aamarpay" | "shurjopay" | "sslcommerz" | "bkash" | "portwallet";

export interface GatewayCapabilities {
  /** How credentials work. Drives the connect form and the token lifecycle (section 8). */
  auth: "static_keys" | "bearer_token";           // aamarPay/SSLCommerz: keys in each request; shurjoPay: short-lived token
  /** Flow shape. `redirect`: create a session, send the customer to a hosted page (all current gateways). */
  checkout: "redirect";
  /** `merchant_reference`: the gateway rejects a repeated reference. `none`: it accepts duplicates (aamarPay), so uniqueness is ours. */
  referenceUniqueness: "enforced" | "not_enforced";
  maxReferenceLength: number;                      // aamarPay 32
  /** How the final result reaches us besides the customer's browser. */
  serverNotification: "ipn" | "none" | "unverified"; // `unverified`: exists but not confirmed, we do not rely on it
  verify: { byGatewayRef: boolean; byMerchantRef: boolean };
  currencies: string[];                           // P1: ["BDT"]
  refund: "api" | "manual_only" | "unknown";
  partialRefund: boolean;
  feeReported: boolean;                           // gateway tells us its fee / net amount
  methods: string[];                              // informational: cards, bkash, nagad, rocket, bank ... (not selectable per attempt in P1)
  sandbox: { available: boolean; sharedCredentials: boolean };
  customerFieldsRequired: ("name" | "email" | "phone" | "address" | "city")[];
}

export interface PaymentGatewayAdapter {
  readonly id: GatewayId;
  readonly capabilities: GatewayCapabilities;

  /** Cheap authenticated call that proves the credentials work. Never a payment. */
  validateCredentials(ctx: GatewayContext): Promise<ValidateResult>;

  /** Create a hosted checkout session. Throws GatewayError; a thrown timeout is `unknown`, see 6.2. */
  initiate(ctx: GatewayContext, req: InitiateRequest): Promise<InitiateResult>;

  /** Ask the gateway what happened. Server-to-server, uses the workspace's credentials. The only source of `paid`. */
  verify(ctx: GatewayContext, ref: VerifyRef): Promise<VerifyResult>;

  /** Read the customer's return (GET query or POST form). Returns a *hint*: which attempt, what the browser claims. No trust. */
  parseReturn(req: RawRequest): ReturnHint;

  /** Only when serverNotification === "ipn". Authenticate (signature or none + mandatory verify) and parse. */
  parseNotification?(req: RawRequest, ctx: GatewayContext): Promise<NotificationHint>;

  refund?(ctx: GatewayContext, req: RefundRequest): Promise<RefundResult>;
}

export interface GatewayContext {
  account: { id: string; mode: "sandbox" | "live"; credentials: Record<string, string>; config: Record<string, unknown> };
  baseUrl: string;   // from the registry; overridable only when NODE_ENV !== "production"
  signal: AbortSignal;
}
```

### 4.1 Normalized input and output

```ts
interface InitiateRequest {
  reference: string;            // ours, section 6.1
  amountMinor: number;          // poisha
  currency: "BDT";
  description: string;
  customer: { name: string; email?: string; phone: string; address?: string; city?: string };
  returnUrls: { success: string; fail: string; cancel: string };   // all point at our public return endpoint (section 7)
  notificationUrl?: string;     // our IPN endpoint when the gateway supports it
  passthrough: { attemptId: string };  // echoed back by gateways that support custom fields
}
interface InitiateResult { checkoutUrl: string; gatewayRef?: string; expiresAt?: Date; raw: unknown /* redacted */ }

type VerifyRef = { reference: string; gatewayRef?: string };
interface VerifyResult {
  status: "paid" | "failed" | "cancelled" | "expired" | "pending" | "not_found";
  amountMinor?: number; currency?: string;           // what the gateway says was paid
  gatewayTxnId?: string; bankTxnId?: string; method?: string; payerRef?: string;
  feeMinor?: number; netMinor?: number;
  paidAt?: Date;
  raw: unknown;                                      // stored redacted on PaymentAttempt.raw_response
}
```

### 4.2 Unified attempt status

`created -> redirected -> paid | failed | cancelled | expired`, plus the side states `pending` (customer is paying or the gateway has not settled), `unknown` (we could not tell, section 6.2) and `needs_review` (paid but wrong amount, wrong currency, or paid after the link expired).

| Unified | Meaning | Terminal |
| --- | --- | --- |
| `created` | Row exists, gateway not called yet | no |
| `redirected` | Gateway returned a checkout URL; customer may be paying | no |
| `pending` | Gateway says initiated/processing | no |
| `paid` | Verified paid, amount matches | yes |
| `failed` | Gateway says failed/declined | yes |
| `cancelled` | Customer cancelled at the gateway | yes |
| `expired` | Gateway session or our link expired unpaid | yes |
| `unknown` | Initiate outcome ambiguous (timeout after send) | no, resolved by recheck |
| `needs_review` | Money moved but we cannot accept it automatically | no, Finance decides |

No-regression rule: terminal states never change except `failed|cancelled|expired -> paid` when a **verified** later check proves payment (customers do pay after a "failed" redirect); that transition lands in `needs_review` if the link was already expired or the order already paid by another attempt.

### 4.3 Normalized errors

`GatewayError { code, retriable, message, raw? }` with codes: `auth_failed`, `account_restricted`, `invalid_request` (our bug or bad data; includes `reference_too_long`, `currency_unsupported`), `amount_unsupported`, `not_found`, `rate_limited`, `gateway_down`, `timeout`, `bad_response`. Only `timeout`, `gateway_down`, `rate_limited` are retriable, and **never `initiate` after a possible send** (section 6.2).

## 5. Gateway account (per workspace)

`PaymentProviderAccount` (name kept from `09`): `id (pga_), workspace_id, provider, mode, label, credentials_encrypted, credentials_fingerprint, config (JSON, non-secret), enabled, status (active|error|paused), last_validated_at, last_error_code?, created_by`.

- **Connect.** Admin/Finance picks a gateway, enters that gateway's fields (dynamic form from the registry: aamarPay `store_id` + `signature_key`; shurjoPay `username` + `password` + `prefix`; ...). The server runs `validateCredentials` before saving; a failure is shown with the normalized code and nothing is stored.
- **Validation on demand and daily.** At most 3 attempts per workspace per 5 minutes. `auth_failed` flips the account to `error` and stops creating attempts on it (no auto-retry on a bad credential; some gateways lock accounts).
- **One live account, one workspace.** Unique `(provider, credentials_fingerprint)` where `mode = live`. Sandbox accounts are exempt because several gateways publish **shared** sandbox credentials (aamarPay `aamarpaytest`, shurjoPay `sp_sandbox`) that every developer uses.
- **Several accounts per workspace** are allowed (e.g. bKash and aamarPay). Each has `enabled` and a `priority`; the workspace chooses a default per channel/order type (`09` FR-PAY-02). A link may offer one account in P1; offering several on the hosted page is P2.
- **Never shown after save:** secrets are masked (last 4 characters at most, never for passwords). Rotating keys requires re-validation; history is kept in the audit log, not the row.
- **Permissions:** configure = Owner/Admin/Finance (`payment.provider.manage`); view keys masked.

## 6. Initiating a payment

### 6.1 References

`reference = "pa" + ULID(26)` of the `PaymentAttempt` id, i.e. 28 characters, ASCII alphanumeric only. It fits aamarPay's 32 limit, is unique by construction, and is meaningless to anyone who sees it at the gateway. The `Order.number` and the link id go into the description and the gateway's free-text/custom fields where available (for support), never into the reference. A retry is a **new attempt with a new reference**.

### 6.2 Attempt state machine and unknown outcomes

```text
create link (idempotent on Idempotency-Key) ──► customer opens /pay/{token}
  ──► PaymentAttemptService.start(link):
      Tx1: lock link; require status=active and not expired; require no other attempt in created|redirected|pending|unknown
           younger than the gateway session lifetime (else reuse its checkout URL if still valid); insert attempt(created)
      call adapter.initiate (outside any DB transaction, 10 s timeout, no retry)
      Tx2: success -> attempt(redirected, checkout_url, gateway_ref); error -> attempt(failed|created) with code
      redirect the customer to checkout_url
```

- A **timeout or connection reset after the request was sent** leaves the attempt `unknown`. We cannot know whether the gateway created a session. Resolution when `verify.byMerchantRef` is true: `verify(reference)`; `not_found` means safe to start a new attempt (new reference), anything else adopts the result. When the gateway can only verify by its own id (`byMerchantRef: false`, shurjoPay) an `unknown` attempt **cannot be resolved automatically**: it is expired with the link, never reused, and a customer claim of payment goes to Finance as `needs_review (unknown_initiate)` to be matched in the gateway panel. For gateways with `referenceUniqueness: "not_enforced"` this check is the *only* protection, so never retry `initiate` with the same reference.
- Only one open attempt per link (partial unique index on `(payment_link_id) WHERE status IN ('created','redirected','pending','unknown')`).
- The hosted page `/pay/{token}` (09 FR-PAY-11) is the only caller of `start`. The chat/AI sends the short link, not a gateway URL, so a link survives a gateway outage, can be retried, and expires under our control.

### 6.3 Customer data

Gateways require customer fields we may not have (aamarPay needs email and phone; shurjoPay needs address and city). Rules: take name/phone/address from the order or customer; if email is missing use `noreply+<workspaceSlug>@<platform domain>` (documented per gateway, not hidden); if address/city is missing use the order's shipping address, else `"N/A"`/`"Dhaka"` **only where the gateway documents that it is not validated** (provider doc section 4). The adapter returns `invalid_request` rather than sending garbage when a required field is truly absent.

## 7. Getting the result back (shared pipeline)

Three sources feed one verifier. None of them sets `paid` by itself.

1. **Customer return** (public `GET|POST /v1/payments/return/{provider}/{attemptId}?outcome=success|fail|cancel`). Accepts both methods (some gateways POST a form to the success URL). `parseReturn` extracts hints; we enqueue `payment-verify(attemptId)` and show the customer a neutral "We are confirming your payment" page that polls `GET /pay/{token}/status` for up to 60 s, then shows the final state or "we will message you when it is confirmed".
2. **Server notification (IPN)** where the gateway has one: public `POST /v1/webhooks/payments/{provider}/{accountId}`. Authenticate when the gateway offers a signature; either way enqueue `payment-verify`. The notification body is stored in `WebhookEventLog` (deduplicated by `(provider, event_id or sha256 body)`) and is otherwise ignored.
3. **Reconciliation sweep** (`payment-reconcile`, every 5 minutes): re-verifies attempts in `redirected|pending|unknown` older than 15 minutes (`09` FR-PAY-36) with backoff, until final or until the link expires plus a grace of 24 h (late payers). This is the safety net that makes lost callbacks harmless.

`payment-verify(attemptId)`:

1. Load attempt + account; decrypt credentials; call `adapter.verify`.
2. `decideAttemptOutcome(attempt, verifyResult)` (pure, in `domain/`):
   - `paid` and `amountMinor === attempt.amount_minor` and currency matches -> `paid`.
   - `paid` and the amount or currency differs -> `needs_review` (`amount_mismatch`), order stays unconfirmed, Finance notified (`09` FR-PAY-32).
   - `paid` but the link is `expired|cancelled` or the order is already paid by another payment -> `needs_review` (`paid_after_expiry` | `overpayment`).
   - `failed|cancelled|expired|not_found|pending` -> corresponding state (`not_found` after a redirect is `pending` until the link expires, then `expired`).
3. In one transaction: update the attempt, create or update `Payment` (`status=paid`, `verification=provider_verified`, `provider_txn_id = gatewayTxnId`, `paid_at`, fee fields), set `Order.payment_status`, expire sibling links (`09` FR-PAY-13), write the outbox event `payment.payment.paid` (or `.failed`). The automation that auto-confirms the order reacts to the event (`07` FR-ORD-21), not to the HTTP request.
4. Idempotent by construction: a unique index on `(provider_account_id, provider_txn_id)` and an attempt that is already terminal makes a second verify a no-op (`09` FR-PAY-35, AC-PAY-04).

The same attempt can be verified any number of times concurrently; the row lock on the attempt serializes them.

## 8. Credentials, tokens and rate limits

- `static_keys` gateways send keys in every call; the adapter builds them from the decrypted account and never logs the request body (redaction at the HTTP client).
- `bearer_token` gateways (shurjoPay): the access token belongs to the **account**, is cached in Redis (`pay:tok:{accountId}`), encrypted, with TTL = `expires_in - 60 s`. Refresh is single-flight (per-account lock, re-read, refresh only if still needed). A `401`/"token expired" triggers exactly one refresh and one retry; a second failure flips the account to `error`. The password is stored encrypted because the token endpoint needs it on every refresh.
- Per-account token bucket (default 5 req/s, adapter may lower it); a `429` honors `Retry-After`. A circuit breaker opens per gateway after consecutive `gateway_down`; the hosted page then shows the fallback methods allowed by the workspace (COD or manual MFS; `09` edge cases).
- Non-production base-URL overrides (`<GATEWAY>_BASE_URL`) are ignored when `NODE_ENV=production`, as in the courier client.

## 9. Sandbox vs live

- `PaymentProviderAccount.mode` and `Payment.livemode` (boolean) are set from the account; the UI shows a persistent "SANDBOX" badge on accounts, links, the hosted page and payment rows.
- A `livemode=false` payment is recorded, shown and verifiable, but it **does not** set `Order.payment_status=paid` and is excluded from finance summaries and CSV exports (it shows as "test payment" on the order). A workspace flag `is_test` (internal/demo workspaces) lifts the order restriction so end-to-end demos work.
- Switching an account from sandbox to live means connecting a **new** account (different credentials, different fingerprint), never editing the mode of an existing one with payment history.
- Live requires the environment flag `PAYMENTS_LIVE_ENABLED_GATEWAYS` to list the gateway (dark launch, like `COURIER_ENABLED_COURIERS`). Dev environments default to sandbox only.

## 10. Refunds

Capability driven (`GatewayCapabilities.refund`). `api` -> `RefundService` calls `adapter.refund`, status `requested -> processing -> refunded|failed`. `manual_only | unknown` -> `manual_refund_pending` with instructions for the seller to refund in the gateway's merchant panel and then mark it done with the gateway's refund id (`09` FR-PAY-40..42). Refund amounts are poisha and checked against `paid - already refunded`.

## 11. Observability, audit, privacy

- Audit: account connect/replace/enable/disable/remove, link create/cancel, manual verify, refund request/approve.
- Metrics: attempts started/paid/failed by gateway, time to pay, verify latency, reconcile backlog, `needs_review` count, unknown-outcome count, circuit-breaker state.
- Alerts: reconcile backlog > 50 or oldest pending > 1 h; `needs_review` older than 24 h; validation `auth_failed` on a live account.
- Logs carry `workspaceId, accountId, provider, attemptId, reference`; never credentials, tokens, card fields, customer PII beyond ids.
- Raw gateway responses are stored on `PaymentAttempt.raw_response` after redaction (drop `card_number`, `card_holder_name`, email/phone fields are kept only if needed for dispute and are covered by the retention policy).

## 12. Testing strategy

1. **Unit:** `decideAttemptOutcome` table tests (every verify status x amount x link/order state), reference builder, poisha <-> decimal conversion (exhaustive, including `.5` taka and rounding refusals), redaction.
2. **Conformance suite** (`gateway-conformance.spec.ts`) runs against every adapter and its fake server: initiate ok, initiate invalid credentials, verify paid / failed / cancelled / pending / not_found, timeout on initiate -> `unknown`, double verify, wrong amount, amount in a different currency, secrets never in logs.
3. **Fake gateway servers** (`pnpm --filter @unifaio/api fake:aamarpay|fake:shurjopay`) with failure modes: slow, 5xx, malformed JSON, expired token, duplicated reference, paid after cancel.
4. **Sandbox smoke** (opt-in, `PAYMENT_SANDBOX_E2E=1`, never in CI by default): validate, initiate, verify of an unpaid attempt against the real sandbox. A *paid* sandbox run needs a human at the hosted page and is a manual test script in the runbook.
5. **Integration (real Postgres/Redis, fake gateways):** link -> hosted page -> start -> fake pay -> return -> verify -> payment paid -> order paid -> event emitted; lost return handled by the sweep; webhook replay; cross-tenant 404 on every endpoint; RLS isolation for the new tables.

## 17. Acceptance criteria (framework level)

- **AC-PAYGW-01** Connecting aamarPay with valid sandbox credentials succeeds; with a wrong `signature_key` it is rejected with `auth_failed` and nothing is stored.
- **AC-PAYGW-02** Two workspaces cannot connect the same live account; both can connect the shared sandbox account.
- **AC-PAYGW-03** Secrets never appear in API responses, logs, audit entries or error messages (redaction test).
- **AC-PAYGW-04** Opening a link twice quickly creates exactly one open attempt and one gateway session.
- **AC-PAYGW-05** A success redirect without a paid verification (forged return) leaves the payment unpaid.
- **AC-PAYGW-06** A verified payment whose amount differs by 1 poisha ends in `needs_review`, order unconfirmed, Finance notified.
- **AC-PAYGW-07** If the customer's return is lost, the sweep marks the payment paid within 20 minutes of the gateway confirming it.
- **AC-PAYGW-08** An `initiate` timeout leaves `unknown`; the next recheck either adopts the gateway session or allows a new attempt with a new reference; no double charge is possible.
- **AC-PAYGW-09** A sandbox payment never sets a live order to paid and does not appear in finance totals.
- **AC-PAYGW-10** Adding a new gateway touches only its adapter folder, the registry, i18n and docs.
